Part A - Questions

1. Continuous Integration, Continuous Delivery and Continuous Deployment

Continuous Integration (CI) means that changes made to the source code are automatically built and tested regularly. For example, when I push my backend code to GitHub, GitHub Actions can automatically build the Docker container image. This helps detect problems early.

Continuous Delivery extends CI by preparing a successful build so that it is ready to be released. The deployment can still require a manual action or approval.

Continuous Deployment goes one step further. If the automated process succeeds, the new version is deployed automatically without requiring a manual deployment step.

In my Week 6 project, a push to the main branch starts the pipeline, builds and pushes the backend image and then updates the backend Deployment in Rahti.

2. Structure of a GitHub Actions Workflow

A GitHub Actions workflow mainly contains triggers, jobs and steps. A trigger defines when the workflow starts. For example, my workflow uses a push to the main branch as a trigger.

A job is a collection of work that runs on a runner. Inside each job there are steps. The steps are executed in order and can run commands or reusable GitHub Actions.

My pipeline checks out the repository, creates the container image name, builds the backend Docker image, logs in to GHCR, pushes the image, installs the OpenShift CLI, logs in to Rahti, selects the project and updates the backend Deployment.

3. Deployment Automation Patterns

An imperative CLI pipeline directly connects to the cluster and runs commands such as oc set image. This method is simple and easy to understand, but the CI system needs credentials that allow it to access the cluster.

An ImageStream trigger allows OpenShift to watch for a new container image. When a new image becomes available, OpenShift can automatically start a new deployment. This reduces the amount of direct cluster interaction required from the CI pipeline.

GitOps uses a tool such as Argo CD to continuously compare the desired configuration stored in Git with the actual cluster state. This can reduce the need to expose cluster credentials outside the cluster.

For this assignment I used the imperative CLI approach because GitHub Actions logs into Rahti and runs OpenShift commands directly.

4. Three Pillars of Observability

The three main pillars of observability are metrics, logs and traces.

Metrics are numerical measurements over time. They can answer questions such as how much CPU or memory a pod is using or how many requests the application receives.

Logs are timestamped records produced by an application. They can answer questions such as which endpoint was requested, what status code was returned, and whether an error occurred.

Traces show the path of an individual request through multiple services. They can help identify which service caused a slow or failed request in a distributed application.

5. Liveness Probe vs Readiness Probe

A liveness probe checks whether a container is still alive and working. If the liveness probe repeatedly fails, Kubernetes can restart the container.

A readiness probe checks whether the container is currently ready to receive traffic. If readiness fails, Kubernetes keeps the container running but removes the pod from the Service's available endpoints until it becomes ready again.

In my application both probes normally check the /healthz endpoint on port 8000.

6. Alert Fatigue

Alert fatigue happens when a system produces too many low-value notifications. If developers receive alerts too frequently, they may start ignoring them, including important alerts.

For a small student application I would create only a few useful alerts. For example, I would alert when the application remains unavailable, when requests repeatedly return server errors, or when the database cannot be reached. I would avoid creating an alert for every small temporary change.

7. Why Secrets Should Not Be Hard-Coded

Secrets such as registry passwords and Rahti API tokens should never be written directly inside a workflow file because the workflow is stored in Git. Anyone who can access the repository could potentially see a committed credential.

GitHub Actions provides repository secrets for storing sensitive information. In my pipeline I stored the Rahti server and Rahti token as GitHub repository secrets and referenced them from the workflow. The actual token is therefore not written directly into deploy.yml.

Part B - Automate & Observe My Application

Part 1 - CI/CD Pipeline

I created a GitHub Actions workflow inside: 

.github/workflows/deploy.yml

The workflow runs whenever code is pushed to the main branch.

The automated process is:

Git Push
    ↓
GitHub Actions
    ↓
Build Backend Docker Image
    ↓
Push Image to GHCR
    ↓
Login to Rahti
    ↓
Apply Deployment Configuration
    ↓
Update Backend Image
    ↓
Wait for Successful Rollout

GitHub Actions Workflow

name: Build and Deploy Backend

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set image name
        run: |
          echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}/backend:${GITHUB_SHA}" >> $GITHUB_ENV

      - name: Build backend container image
        run: |
          docker build -t "$IMAGE" ./backend-week5

      - name: Login to GitHub Container Registry
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin

      - name: Push backend image
        run: |
          docker push "$IMAGE"

      - name: Install OpenShift CLI
        run: |
          curl -LO https://mirror.openshift.com/pub/openshift-v4/clients/ocp/stable/openshift-client-linux.tar.gz
          tar -xzf openshift-client-linux.tar.gz
          sudo mv oc /usr/local/bin/oc
          oc version --client

      - name: Login to Rahti
        run: |
          oc login \
            --token="${{ secrets.RAHTI_TOKEN }}" \
            --server="${{ secrets.RAHTI_SERVER }}"

      - name: Select Rahti project
        run: |
          oc project cloudservice-week2

      - name: Apply backend deployment configuration
        run: |
          oc apply -f backend-deployment.yaml

      - name: Deploy new backend image
        run: |
          oc set image deployment/backend backend="$IMAGE"

      - name: Wait for rollout
        run: |
          oc rollout status deployment/backend --timeout=180s

Part 2 - Basic Observability

I added a health endpoint to the Flask backend. Kubernetes can use this endpoint to check whether the backend is healthy. 

@app.route("/healthz")
def healthz():
    return jsonify({
        "status": "healthy"
    }), 200

Liveness and Readiness Probes

I configured both a liveness probe and a readiness probe in the backend Deployment. 

livenessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 15
  timeoutSeconds: 3
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

Screenshot 4 - Backend Pods Running and Ready

The backend pods are Running and show 1/1 Ready. This demonstrates that the backend is healthy and the readiness checks are succeeding.

Structured Backend Logging

I added structured request logging to the Flask backend. For every request, the application records the HTTP method, request path, response status code and response time. 

@app.before_request
def start_timer():
    request.start_time = time.time()


@app.after_request
def log_request(response):
    duration_ms = round(
        (time.time() - request.start_time) * 1000,
        2
    )

    logger.info(
        "method=%s path=%s status=%s response_time_ms=%s",
        request.method,
        request.path,
        response.status_code,
        duration_ms
    )

    return response

Screenshot 5 - Structured Backend Logs

The backend logs show GET requests to /healthz with HTTP status 200 and response times. These requests demonstrate that the health endpoint is being checked while the application is running.

Readiness Probe Failure Test

I also deliberately tested the readiness probe. I temporarily changed the readiness endpoint from: 

path: /healthz

to an invalid endpoint:

path: /wrong-health

After deploying this change, the backend container continued running, but the new pod changed to 0/1 Ready. This demonstrated that a readiness probe failure makes Kubernetes consider the pod not ready to receive Service traffic without immediately stopping the running container.

After the test I changed the readiness endpoint back to /healthz, committed the correction and pushed it to GitHub. The CI/CD pipeline automatically deployed the corrected configuration, and the backend returned to 1/1 Ready.

Problems Encountered and Solutions

Incorrect Rahti Project Namespace

The first GitHub Actions run successfully built the backend image, logged in to GHCR, pushed the image and logged in to Rahti. However, it failed when selecting the Rahti project.

The original command was:

oc project cloudservices-week2

Rahti reported that I was not a member of this project and showed that the actual project name was: 

cloudservice-week2

I corrected the workflow to:

oc project cloudservice-week2

I then committed and pushed the correction. Because the workflow runs on pushes to the main branch, GitHub Actions started another pipeline automatically. The second pipeline completed successfully.

Final Result

The final CI/CD pipeline automatically builds a new backend Docker image, pushes the image to GitHub Container Registry and deploys the new version to CSC Rahti.

The backend also has working liveness and readiness probes, a health endpoint and structured request logging.

Reflection and Alerting

This assignment helped me understand how deployment automation and observability work together. Previously, application deployment required more manual steps. With GitHub Actions, a source-code push can automatically create a new container image and deploy it to Rahti.

The readiness test also demonstrated the difference between a process that is running and a service that is actually ready to receive traffic. A container can continue running while Kubernetes marks the pod as unavailable for Service traffic.

Structured logs make troubleshooting easier because they show the requested endpoint, HTTP response status and response time.

Example Alert Rule

One useful real alert could monitor HTTP 5xx responses from the backend. For example, an alert could be triggered if the backend produces a high number of HTTP 500 errors for several minutes.

Another useful alert could be triggered if the backend remains Not Ready for several minutes. I would not create an alert for every temporary readiness failure because short failures can recover automatically. Too many unnecessary notifications could cause alert fatigue.
