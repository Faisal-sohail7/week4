1. Frontend, Backend and Database Communication

The frontend communicates with the Python backend through the REST API. The backend communicates with the MySQL database. The database time and visit counter shown on the application demonstrate that communication between the frontend, backend and database is working.

2. Running Pods

The application components are running in Rahti. The backend, database and frontend application Pods are running successfully.

3. Database Persistence

I tested database persistence by checking the visit counter before recreating a Pod. The application had 6 visits stored in the database.

After the Pod was recreated, the application still showed 6 visits. This demonstrates that the application data was not lost when the Pod was recreated and that persistent storage works.

4. Pod Recovery

I tested Pod recovery by deleting a running Pod in Rahti. Kubernetes automatically created a replacement Pod. The new Pod reached the Running state, showing that the Deployment maintains the required number of replicas automatically.

5. Scaling Experiment

I tested application scaling by increasing the backend Deployment from one replica to two replicas. Rahti created another backend Pod and both backend Pods reached the Running state. This demonstrates how Kubernetes can scale an application by running multiple replicas.

6. Application Update

The application source code is stored in Git and connected to Rahti. After changes were pushed to the repository, the application was rebuilt and deployed again. Kubernetes used a new Pod for the updated application while the Deployment continued to manage the application. This demonstrates the application update and rollout process.

7. Problems and Solutions

One of the main problems was communication between the frontend and the backend. The frontend initially returned an HTTP 404 API error. I checked the frontend request and Nginx configuration and corrected the proxy configuration so that API requests were forwarded to the backend service correctly.

I also had to make sure that the backend, database and frontend services were running correctly and that their Kubernetes Services and Deployments were connected using the correct names and ports. After correcting the configuration, the database time and visit counter worked correctly.

8. Rahti Compared with Docker Compose and cPouta

In the previous Docker Compose and cPouta deployment, containers were managed mainly through Docker Compose on a virtual machine. In Rahti, Kubernetes resources such as Deployments, Services, ConfigMaps and persistent storage are used to deploy and manage the application.

Rahti also provides automatic Pod recovery and easy scaling. When a Pod is deleted, Kubernetes can create a replacement automatically. The number of application replicas can also be changed without manually starting separate containers. Networking is handled through Kubernetes Services, while a Route provides public access to the application.
