Part A - Questions

1. What is the difference between SAML and OAuth?

SAML (Security Assertion Markup Language) and OAuth are both used in identity and access management, but they solve different problems. SAML is mainly used for authentication and Single Sign-On (SSO). It allows a user to authenticate with an identity provider and then access another service without signing in again.

For example, a company could use SAML so that employees can use one company account to access several internal web applications. SAML commonly exchanges authentication information using XML-based assertions between an identity provider and a service provider.

OAuth, on the other hand, is mainly an authorization framework. It allows an application to receive limited access to another service without requiring the user to give the application their password. For example, an application could receive permission to access selected information from another service using an access token.

A company may therefore choose SAML when it needs enterprise SSO and centralized authentication. OAuth is more appropriate when an application needs permission to access another service or API on behalf of a user. OAuth can also be combined with OpenID Connect when authentication information is required.

2. What is a Web Application Firewall (WAF)?

A Web Application Firewall is a security system that monitors and filters HTTP and HTTPS traffic going to a web application. Unlike a traditional network firewall that mainly works with addresses, ports and protocols, a WAF can inspect web requests at the application layer.

A WAF can help defend a web application against attacks such as SQL injection, cross-site scripting (XSS), malicious HTTP requests and some automated attacks. Rules can be used to block suspicious requests before they reach the application.

In my Rahti architecture, a WAF would ideally be placed before the public frontend, between Internet users and the Route. This means malicious traffic could be filtered before it reaches the Nginx frontend or Flask backend.

The flow could therefore be: Internet → WAF → Route → Nginx frontend → Flask backend → database.

3. Decentralized storage compared with centralized object storage

Centralized object-storage systems such as CSC Allas or Amazon S3 are managed through a centralized cloud service. The provider manages the infrastructure and users normally upload and retrieve objects through the provider's interfaces or APIs.

A decentralized or cooperative storage system distributes data between multiple participating nodes instead of depending on one centralized storage provider. Systems such as IPFS can use content-based addressing to identify and retrieve data.

Decentralized storage can provide advantages such as distribution, redundancy and less dependence on a single provider. However, it can also make management more complicated. Availability, performance, privacy, access control, deletion and regulatory requirements may be more difficult to manage.

Centralized object storage is generally easier to administer and provides predictable APIs and provider support, while decentralized storage can provide greater distribution at the cost of additional operational complexity.

4. What is YAML and why is it used with Kubernetes?

YAML is a human-readable data serialization format. Kubernetes and OpenShift commonly use YAML files to describe resources such as Deployments, Services, ConfigMaps, Secrets and PersistentVolumeClaims.

YAML is useful for Kubernetes because configuration can be written in a structured form while remaining relatively easy for humans to read. For example, the number of replicas, container image, environment variables and container ports can all be described in one Deployment manifest.

JSON can represent the same kind of structured information, but it uses braces, brackets and more quotation marks. YAML is usually less visually cluttered, which is useful for large Kubernetes manifests. YAML also supports comments.

One disadvantage is that indentation is important in YAML. Incorrect indentation can change the structure of a configuration or cause it to fail. During this project I used YAML to configure resources such as Deployments and Services in Rahti.

Part B - Hands-On: Redis Cache Extension

1. Objective

In Week 4 I deployed a three-container application consisting of an Nginx frontend, a Flask backend and a MySQL database on CSC Rahti. For Week 5 I selected Option 2: Add a Redis Cache.

I added Redis as a separate Deployment and Service. I also created an updated Flask backend that contains the Python Redis client. The backend communicates with Redis using the internal Redis Service on port 6379.

The original frontend, backend and MySQL functionality continues to work while Redis provides an additional cache component.

3. Redis Deployment and Service

Redis was deployed as its own Deployment instead of installing Redis inside the Flask container. This follows the same orchestration pattern used for the other application components.

The Redis Deployment runs a Redis container and exposes port 6379. A ClusterIP Service named redis provides an internal network endpoint for the backend.

Because Kubernetes/OpenShift provides internal DNS for Services, the Flask backend can use the hostname redis instead of depending on the Redis Pod's IP address.

4. Backend Configuration

The Week 4 backend image did not contain the Python Redis library. Therefore, I created a new Week 5 backend image containing Flask, Gunicorn, PyMySQL and the Redis Python client.

The backend was configured with the following Redis connection information:

REDIS_HOST=redis
REDIS_APP_PORT=6379

The existing database configuration continues to come from the application's ConfigMap and Secret. Database credentials are not stored directly in the application source code.

5. Redis Integration

I added an /api/cache endpoint to the Flask backend. The endpoint first checks Redis for a cached value.

If the value does not exist, the backend stores Hello from Redis! in Redis with a limited lifetime. When the endpoint is requested again, the value is retrieved from the Redis cache.

This demonstrates that Redis is not only running as another Pod. The Flask application is actually communicating with it and using it as a cache.

The following terminal test was executed from the Week 5 Flask backend. The Redis connection returned True. The first API request stored a new value in Redis and the second request retrieved the existing value from the cache.

7. Evidence - Original Week 4 Application Still Works

After adding Redis and the updated backend, the original application continued to communicate with MySQL. The database time and visit counter demonstrate that the frontend, backend and database flow remains operational.

The Pods view shows Redis running as its own Pod together with the Week 5 backend and the existing application components. This proves that Redis was deployed as an orchestrated component rather than being added inside another container.

10. Security and Production Readiness

The current Redis configuration is suitable for demonstrating the architecture in this course, but a production system would require additional security and reliability measures.

Redis should normally remain an internal service and should not be exposed directly to the public Internet through a Route. Access should be limited to the application components that require it. NetworkPolicies could also be used to restrict which Pods are allowed to communicate with Redis.

If Redis authentication credentials were required, they should be stored in a Kubernetes/OpenShift Secret instead of being committed to Git. Production deployments may also require TLS, Redis ACLs, resource limits, monitoring and health checks.

Reliability is also important. If Redis is used only as a cache, the application should continue operating when cached data is lost. If Redis stores important state, persistence, backups and replication would need to be considered.

11. Cache Invalidation

One important reliability issue with caching is cache invalidation. Cached information can become outdated when the original data changes. An application therefore needs a strategy for deciding when cached data should be removed or refreshed.

In my demonstration, the cached value is stored with a time limit. This means Redis automatically removes the value after the configured time and the application can create a new cached value later. In a real application, different types of data could require different expiration times.

12. Connection to Part A

The security ideas discussed in Part A also apply to this architecture. A Web Application Firewall could be placed before the public Route to filter malicious web requests before they reach the frontend and backend.

Redis itself should remain inside the cluster and should not be exposed publicly. ConfigMaps are useful for non-sensitive configuration, while Secrets should be used for passwords and other sensitive values.

YAML is also directly related to this implementation because Rahti resources such as Deployments and Services can be defined using YAML manifests.

13. Problems Encountered and Solutions

Problem 1 - Existing backend did not support Redis:
The original Week 4 backend image did not contain the Python Redis module. Running a Python import test returned a ModuleNotFoundError.

Solution:
I created a new Week 5 backend with the Redis Python package included in its requirements. This allowed Flask to communicate with the Redis Service.

Problem 2 - Gunicorn permission error:
The first version of the new backend used Gunicorn 26.2.0. On Rahti it produced a permission error related to /.gunicorn.

Solution:
I used Gunicorn 23.0.0 for the course backend. After rebuilding the image, Gunicorn started correctly and the Flask application ran on port 8000.

Problem 3 - Connecting the frontend to the new backend:
The existing frontend was originally connected to the Week 4 backend through the backend Service.

Solution:
The backend Service was configured to select the new Week 5 Flask backend. This allowed the existing Nginx configuration to continue using the same backend Service name while the requests were handled by the Redis-capable backend.

Problem 4 - Backend Route showed 404:
Opening the automatically created Week 5 backend Route at its root URL displayed a 404 Not Found page.

Solution:
This was expected because the Flask backend provides API endpoints rather than a homepage at /. The application's public webpage is provided by the Nginx frontend Route, while Flask handles endpoints such as /api/status and /api/cache.

14. Final Result

The Week 4 three-container application was successfully extended with Redis as a fourth application component. Redis runs as its own Deployment and Service, the Flask backend communicates with it, and the cache functionality was verified by storing and retrieving a value. The original frontend-to-backend-to-MySQL functionality also continues to work.
